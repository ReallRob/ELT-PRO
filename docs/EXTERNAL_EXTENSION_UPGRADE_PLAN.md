# 外置扩展升级计划

本文档记录代码块第三方依赖的后续升级方向。目标是在不重新打包设计器或 CRPA 运行器的前提下，从企业内网的受控扩展源补齐代码块缺少的第三方包；不访问公网，也不在目标机器执行 `pip install`。

## 当前实现

当前版本已经支持手工外置扩展：

- 在“打包依赖”页将依赖标记为“外置扩展”。
- 从配置 Python 的本地 `site-packages` 复制发行包、其 `.dist-info`、数据文件、DLL 和已安装依赖，生成 ZIP。
- 在目标程序导入并合并启用 ZIP；导入 `requests` 时会保留当前环境中的 `selenium`，构建新的完整快照后启用。相同发行包的不同版本会要求用户确认更新。
- 扩展版本以完整快照保存；运行时只加载 `active.json` 指向的一个版本，旧版本仅用于回滚。
- “新建扩展清单”使用独立的空草稿生成 ZIP，不会清空或覆盖程序内置依赖清单；归档内的 `manifest.json` 会记录根包及全部递归发行包的实际版本。

当前实现不联网，也不会在代码块运行时自动补齐缺失包；ZIP 仍需要由发送方生成并手工导入。

## 下一阶段：内网源增量加载

### 内网扩展源

内网指定一台受控机器维护**唯一一套权威 `site-packages`**。管理员负责安装、升级和验证其中的第三方包；源环境发布前必须执行依赖检查，例如 `pip check`。

扩展源需要提供包目录或服务接口，使运行器能按“根模块 / 发行包”请求依赖闭包。例如请求 `requests` 时，扩展源返回：

```text
requests
urllib3
certifi
charset-normalizer
idna
```

每次返回还必须携带发行包版本、Python 主版本、架构、文件清单和校验值。目标程序只从该内网源下载，不访问 PyPI 或其他公网源。

### 运行器加载流程

1. 代码块开始前扫描静态 `import`；运行时 `ModuleNotFoundError` 作为动态 import 的兜底检测。
2. 发现缺少 `requests` 时，运行器请求内网扩展源导出 `requests` 的完整依赖闭包。
3. 运行器将内网版本清单与当前扩展清单比较。
4. 没有版本差异时，将新包和依赖加入临时环境。
5. 存在版本差异时，显示“新增包、旧版本 -> 新版本、可能受影响的根包”，由用户选择“取消”或“下载并更新”。
6. 用户确认后，以“当前全部外置包 + 新包”的结果构建新的完整临时 `site-packages`，校验成功后原子切换为当前扩展环境。
7. 保留旧快照用于回滚；新启动的代码块进程使用新环境，已运行进程不强行替换已导入模块。

这里的“加入”是逻辑上的增量加载。实现上不得直接在正在使用的 `site-packages` 覆盖文件；必须在临时目录完成复制、删除旧文件和校验后再切换，避免残留旧 `.dist-info`、DLL 或半更新状态。

### 版本不一致的处理规则

同一个当前扩展环境中，一个发行包只允许一个版本。发现版本不一致时，默认不静默覆盖，应提示用户确认，例如：

```text
新增：requests 2.32.3
更新：urllib3 1.26.18 -> 2.2.2
受影响的已安装根包：selenium
```

用户确认更新后，新版本覆盖的是**完整扩展快照**，不是只覆盖 `urllib3/` 文件夹。源环境是版本权威：若源环境本身无法为现有外置包和新包提供兼容版本组合，则拒绝发布和更新，并显示依赖冲突原因。

## 更远期：隔离环境

“一个统一扩展环境”适用于公司内统一维护、版本兼容的常见代码块依赖。当两个库确实无法共享底层依赖版本时，不能在同一个 `site-packages` 强行放两份。

届时再升级为“工作流绑定扩展 profile + 代码块独立子进程”：每个 profile 仍只有一套统一 `site-packages`，不同 profile 在不同子进程中运行。这是较大工程，当前不纳入内网增量加载的首期范围。

## 验收条件

- 运行器只从配置的内网扩展源获取包，不访问公网。
- 缺少外置包时能展示将下载的根包和递归依赖。
- 版本不一致时必须先展示差异并等待确认。
- 更新失败、网络中断或校验失败后，旧扩展环境仍可正常使用。
- 当前扩展环境中不保留同一发行包的多个版本。
- 更新后的依赖仅对新启动的代码块进程生效；旧快照可以回滚。
